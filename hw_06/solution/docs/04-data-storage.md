# 4. Хранение данных

## 4.1 Выбор БД с обоснованием

Критерии выбора — из требований (01) и архитектуры (02):

1. **Режим данных.** Для денег и мест нужен строгий ACID (N-14 «двойная продажа = 0», N-15 «RPO = 0»); для каталога, поиска, очереди и кэша достаточно скорости и итоговой согласованности (2.3).
2. **Неравномерная нагрузка.** Пик чтения 10 000 RPS при 40 000 одновременных пользователей на онсейле (N-03) против спокойных 20 RPS в среднем — read-хранилища должны переживать всплеск ×500.
3. **Latency-бюджеты.** Схема зала — p99 800 мс (N-10), hold — p99 1,5 с (N-11), поиск — p50 200 мс.

Сводная таблица:

| Домен | Хранилище | Ключевая причина |
| --- | --- | --- |
| Заказы, платежи, билеты, места (seat_inventory) | **PostgreSQL** | ACID и строгая консистентность: двойная продажа (N-14) и потеря платежа (N-15) недопустимы |
| Холды мест, кэш, waiting room, rate-limit | **Redis** (master + реплики) | Атомарный захват с TTL за O(1) и отклик < 1 мс при пике чтения 10 000 RPS (N-03, N-10) |
| Поиск и автоподсказки | **Elasticsearch** | Полнотекстовый поиск с русской морфологией и fuzzy-опечатками (F-C-03) |
| Аналитика продаж | **ClickHouse** | Дашборды организатора по всем продажам с обновлением ≤ 1 мин (F-B-04) |
| Статика: шаблоны схем залов, изображения, выгрузки | **S3** | Большие неизменяемые файлы, версионирование, раздача через CDN (шаблоны — иммутабельные ключи, кэш навсегда) |
| PDF-билеты | **S3** | Персональные файлы покупателя — отдача по presigned URL напрямую, без edge-кэша CDN |

### 4.1.1 PostgreSQL — источник истины

**Что храним:** пользователи, организаторы, площадки, события, места (seat_inventory), заказы, билеты, платежи, возвраты, outbox, audit-журнал.

**Почему подходит:**

- Транзакция «подтверждение оплаты → перевод мест в SOLD → запись outbox-события» выполняется либо целиком, либо никак (ADR-003, ADR-001). Это единственная гарантия, которая закрывает N-14 и N-15.
- FK и CHECK-констрейнты не дают сохранить битые данные (заказ без пользователя, платёж без заказа).
- Redis может ошибиться или отвалиться, поэтому при подтверждении оплаты PostgreSQL ещё раз проверяет каждое место: строка блокируется на время транзакции (`SELECT ... FOR UPDATE`), а поле `version` не даёт перезаписать место, если его уже трогал другой заказ. Оверселл становится невозможен даже при сбое Redis.
- Репликация и бэкапы — [06-reliability](06-reliability.md) (6.2): синхронная реплика в другой AZ даёт RPO = 0 (N-15), WAL-архив — PITR (N-21).

### 4.1.2 Redis — горячие данные

**Что храним:** холды мест, агрегаты доступности, сессии, JWT-blacklist, rate-limit-счётчики, waiting room, кэш каталога и поиска.

**Почему подходит:**

- Холд места — это `SET key hold_id NX PX 600000`: атомарный захват и авто-освобождение через 10 минут (F-C-07, ADR-001) за O(1), без фоновых чистильщиков.
- In-memory отклик < 1 мс необходим при 10 000 RPS чтения схемы зала в пике (N-03) — диффы статусов уходят клиентам по SSE-потоку (5.2), чтобы уложиться в p99 800 мс (N-10).
- ZSET — готовая структура для виртуальной очереди с позициями (F-C-06); TTL-ключи — готовый rate-limit против ботов (N-20).

### 4.1.3 Elasticsearch — поиск

**Что храним:** поисковый индекс событий, артистов и площадок — read-model, перестраиваемая из потока событий Kafka (2.3).

### 4.1.4 ClickHouse — аналитика

**Что храним:** поток событий продаж и телеметрии из Kafka, аналитическую read-model для дашбордов.

**Почему подходит:** колоночное хранение и сжатие дают агрегации по всем продажам события за секунды — это закрывает F-B-04 (обновление статистики ≤ 1 мин). Сюда же уходят аналитические запросы «все продажи события» (4.3), чтобы они не давили на OLTP.

**Горячее окно и архив:** ClickHouse хранит горячее окно ~12 месяцев (как PostgreSQL, 4.3.1); телеметрия старше окна выгружается в S3+Parquet — холодный архив (объёмы — 3.4): расследования инцидентов, аудит фрода, rebuild при смене схемы.

### 4.1.5 S3 — статика

**Что храним:** шаблоны схем залов JSON (4.2.3), изображения событий, PDF-билеты (F-C-10), выгрузки реестров для СКУД (F-B-05).

**Почему подходит:** большие неизменяемые файлы с версионированием; lifecycle-политики (PDF-билет → удаление через 30 дней после события); раздача через CDN — иммутабельные версии шаблонов кэшируются навсегда. PDF-билеты — исключение: они персональные, отдаются по presigned URL с S3 напрямую, без edge-кэша CDN (03.5).

## 4.2 Схема данных

Данные живут на двух уровнях: **PostgreSQL — источник истины** (4.2.1), **Redis — горячая копия и быстрые структуры** (4.2.2). Геометрия схем залов — в S3 (4.2.3).

### 4.2.1 PostgreSQL: таблицы

**Справочники** (один кластер, 4.3.1):

```text
users — покупатели (User Service)
  user_id      uuid  PK
  email        text  UNIQUE
  phone        text
  name         text
  created_at   timestamptz
  status       text              ACTIVE | BLOCKED (блокировка за фрод, F-A-02)

organizers — организаторы (Organizer Service)
  organizer_id  uuid  PK
  name          text
  status        text             ACTIVE | BLOCKED (модерация, F-A-01)

venues — площадки (Organizer Service)
  venue_id         uuid  PK
  name             text
  city             text
  address          text
  seatmap_version  int           — указатель на актуальную APPROVED-версию шаблона

seatmap_versions — версии шаблона схемы зала (Organizer Service)
  venue_id     uuid   PK, FK -> venues
  version      int    PK
  s3_key       text            — иммутабельный ключ S3
  status       text            DRAFT | APPROVED | REJECTED (апрув, F-A-04)
  uploaded_by  uuid            — организатор-владелец или администратор

events — события (Organizer Service)
  event_id         uuid  PK
  organizer_id     uuid  FK -> organizers
  venue_id         uuid  FK -> venues
  seatmap_version  int          — версия шаблона, зафиксирована при создании события
  title            text
  genre            text
  starts_at        timestamptz
  sale_starts_at   timestamptz
  status           text         DRAFT | PUBLISHED | SALE | CANCELLED | DONE
```

**Таблица мест события** — нумерованные секторы:

```text
seat_inventory — нумерованные места события: одна строка = одно место с ценой и статусом (Booking Service)
  event_id  uuid    PK, FK -> events
  seat_id   text    PK                 — из шаблона схемы, формат {сектор}-{ряд}-{место}
  category  text                       — ценовая категория (разметка события, F-B-01)
  price     bigint                      — цена в копейках
  status    text                        FREE | HELD | SOLD | BLOCKED
  version   int                         — optimistic locking
  INDEX (event_id, status)              — быстрый пересчёт доступности
```

**Таблица зон события** — стоячие зоны и залы без нумерации (F-C-05), продаём количеством, а не местами:

```text
zone_inventory — зоны события: одна строка = одна зона со счётчиками (Booking Service)
  event_id  uuid    PK, FK -> events
  zone_id   text    PK                 — из шаблона схемы (id сектора-зоны)
  category  text                       — ценовая категория (F-B-01)
  price     bigint                      — цена в копейках, одна на зону
  capacity  int                         — квота зоны (может быть меньше физической ёмкости, F-B-01)
  sold      int                         — продано билетов
  version   int                         — optimistic locking
```

Одно событие может иметь и то и другое (стадион: нумерованные трибуны + стоячая фан-зона). Продажа места = строка в `seat_inventory`; продажа в зону = +1 к `zone_inventory.sold`.

**Продажи:**

```text
orders — заказы (Order Service)
  order_id    uuid        PK
  user_id     uuid        FK -> users
  event_id    uuid        FK -> events
  status      text                     PENDING_PAYMENT | PAID | CANCELLED | REFUNDED
  total       bigint                    — сумма в копейках
  created_at  timestamptz
  expires_at  timestamptz               — дедлайн оплаты (10 мин, F-C-07)

tickets — билеты (Ticket Service)
  ticket_id  uuid   PK
  order_id   uuid   FK -> orders
  event_id   uuid   FK -> events
  seat_id    text   NULL, FK -> seat_inventory   — для билетов на конкретное место (F-C-04)
  zone_id    text   NULL, FK -> zone_inventory   — для билетов в зону (F-C-05)
  CHECK (seat_id IS NOT NULL OR zone_id IS NOT NULL)  — ровно одно из двух
  qr_sign    text                       — Ed25519-подпись QR, приватный ключ только на сервере (F-C-10)
  status     text                       ISSUED | USED | REFUNDED

payments — платежи (Payment Service)
  payment_id       uuid    PK
  order_id         uuid    FK -> orders
  amount           bigint
  psp              text             — платёжный провайдер (основной/резервный, F-C-09)
  psp_ref          text             — ссылка операции у провайдера
  status           text             PENDING | SUCCEEDED | FAILED | REFUNDED
  idempotency_key  text   UNIQUE    — ретраи webhook'ов PSP не создают дубли

refunds — возвраты (Order Service)
  refund_id  uuid    PK
  order_id   uuid    FK -> orders
  amount     bigint
  reason     text             — расчёт удержания по правилам (F-C-12)
  status     text
```

**Служебные таблицы:**

```text
outbox — transactional outbox (ADR-003)
  id            bigint   PK
  aggregate_id  uuid            — заказ/платёж/событие
  type          text            — тип события в Kafka
  payload_json  jsonb
  created_at    timestamptz
  sent          boolean

audit_log — журнал операций (N-21, append-only, 3 года)
  id         bigint   PK
  actor      uuid             — кто совершил действие
  entity     text             — заказ / возврат / выплата
  entity_id  uuid
  action     text
  payload    jsonb
  ts         timestamptz
```

**Связи между таблицами:**

```text
users      1 -- N  orders            «мои заказы» (F-C-11)
organizers 1 -- N  events            события организатора
venues     1 -- N  events            события на площадке
venues     1 -- N  seatmap_versions  версии шаблона схемы зала
events     1 -- N  seat_inventory    нумерованные места события
events     1 -- N  zone_inventory    зоны события
events     1 -- N  orders            заказы на событие
orders     1 -- N  tickets           билеты в заказе (до 6, F-C-08)
orders     1 -- N  payments          попытки оплаты (основной/резервный PSP)
orders     1 -- N  refunds           возвраты по заказу
seat_inventory 1 -- 1 tickets        место -> проданный билет
zone_inventory  1 -- N tickets       зона -> проданные в ней билеты
```

Ключевые особенности:

- `seat_inventory.status` меняется `FREE→HELD→SOLD` только с проверкой текущего статуса и `version` (optimistic locking) — второй уровень защиты от оверселла после Redis.
- `zone_inventory.sold` растёт только условием `sold + qty <= capacity AND version = ...` — та же защита от перепродажи зоны, что и для мест.
- `tickets`: CHECK — билет привязан ровно к одному: либо месту, либо зоне.
- `payments.idempotency_key` UNIQUE — ретраи webhook'ов PSP не создают дубли.
- Индекс `(event_id, status)` на `seat_inventory` — быстрый пересчёт доступности.

### 4.2.2 Redis: схема ключей

Ключи одного события содержат hash-tag `{event_id}` — запас на случай будущего шардирования: так все ключи события попадут на один узел, и Lua-скрипты будут работать с ними атомарно. Сейчас кластер одношардовый (1 master + 2 реплики, 06.2.2), поэтому локальность обеспечивается и без hash-tag.

| Ключ | Тип | Значение | TTL | Зачем |
| --- | --- | --- | --- | --- |
| `seat:{event_id}:{seat_id}` | STRING | `hold_id` | 10 мин | Холд нумерованного места (F-C-07, ADR-001): захват `SET NX PX`. Холд создаётся **до** заказа (`POST /holds`), заказ потом ссылается на `hold_id`. TTL — это и есть дедлайн: не оплатил за 10 минут — ключ истекает сам, место возвращается в продажу |
| `zone_hold:{event_id}:{hold_id}` | HASH | `zone_id`, `qty`, `expires_at` | 10 мин | Запись холда зоны: по ней TTL-expiry sweeper возвращает количество в счётчик `avail` (счётчик сам по TTL не восстановится — возвращает sweeper, сверка — reconciler) |
| `user_hold:{event_id}:{user_id}` | STRING | `hold_id` | 10 мин | Один активный холд на пользователя на событие (лимит 6 билетов, N-20): второй `POST /holds` возвращает существующий холд. Заодно — быстрый lookup «мой текущий холд» для таймера в UI |
| `seats:{event_id}` | HASH | `seat_id → FREE\|HELD\|SOLD\|BLOCKED` | без TTL (прогрев) | Полная карта статусов нумерованных мест горячего события — источник для Availability Service (F-C-04); для отрисовки схемы зала. Агрегаты для каталога — отдельный ключ `avail:*` |
| `avail:{event_id}` | HASH | `сектор → свободно сейчас` | без TTL (прогрев) | Cчётчик свободных мест: прогрев `= вместимость`, затем Lua-скрипт холда делает `HINCRBY -qty`, release/sweeper — `HINCRBY +qty`, SOLD не возвращается (до возврата билета). Единый для нумерованных секторов (свободные места) и стоячих зон (свободные билеты, F-C-05). |
| `wr:{event_id}` | ZSET | `user_id → время входа` | 30 мин, heartbeat продлевает | Виртуальная очередь на старте продаж (F-C-06) |
| `wr:admit:{event_id}` | STRING | счётчик допущенных | до конца онсейла | Контролируемый пропуск из очереди внутрь |
| `sess:{session_id}` | HASH | данные сессии | TTL сессии | Сессии пользователей |
| `jwt_bl:{jti}` | STRING | `1` | до истечения токена | JWT-blacklist: выход, блокировка аккаунта (F-A-02) |
| `rl:{route}:{user_id}` | STRING (счётчик) | счётчик запросов | окно (60 с) | Rate-limit против ботов (N-20) |
| `cache:event:{event_id}` | STRING | JSON карточки события | 5 мин | Cache-aside каталога; инвалидация событием `EventUpdated` из Kafka |
| `search:{hash(query)}` | STRING | JSON результатов | 60 с | Кэш популярных поисковых запросов (допускает лёгкую неактуальность) |
| `neg:{type}:{id}` | STRING | `1` | 30 с | Негативный кэш: запросы несуществующих id от ботов не бьют в PostgreSQL |

Правила:

- **Разделение лидерства:** Redis — лидер по холдам (быстрый путь), PostgreSQL — по SOLD (истина). Reconciler раз в 5 минут сверяет held-места с заказами (детали — 4.4.4).
- **Прогрев до старта продаж:** `seats:{event_id}` и `avail:{event_id}` готовятся из PostgreSQL заранее, до открытия продаж (N-23 — ресурсы под онсейл готовятся до пика, а не в момент).
- **Ключи без hash-tag** (`sess:*`, `rl:*`, `cache:*`) — служебные, локальность по событию им не нужна.

Жизненный цикл холда (фазы выбора, release по TTL, генерация `hold_id`, обновление live-доступности) — логика взаимодействия, а не хранения: описана в [ADR-001](../adr/ADR-001-seat-reservation.md).

### 4.2.3 Схема зала (seat map): хранение и вид данных

Схема зала — это **статичная геометрия** (секторы, ряды, места, координаты для отрисовки), **без статусов мест и без цен**. Схемы площадок образуют **общедоступную библиотеку шаблонов**: один шаблон на площадку, им пользуются все организаторы, копий под события не создаётся. Статусы и цены живут отдельно: PostgreSQL `seat_inventory` / `zone_inventory` + Redis (4.2.2), клиент накладывает их поверх геометрии (SSE-поток из 5.3).

Как устроена работа со схемой зала (загрузка, версии, апрув, разметка цен, создание мест) — логика взаимодействия: [ADR-004](../adr/ADR-004-seatmap-template-library.md).

| Данные | Где | Вид |
| --- | --- | --- |
| Шаблон площадки (геометрия) | S3, ключ `s3://static/venues/{venue_id}/seatmap/v{n}.json` | JSON ~30 КБ, иммутабельная версия; указатель актуальной версии — `venues.seatmap_version` |
| Версии шаблона | PostgreSQL `seatmap_versions` | `(venue_id, version)`, статус `DRAFT\|APPROVED\|REJECTED`, ключ S3 |
| Версия события | PostgreSQL `events.seatmap_version` | Фиксируется при создании события; копия в S3 не создаётся |
| Цены и категории события | PostgreSQL `seat_inventory.category/price`, `zone_inventory.category/price` | Одна цена на место/зону, поверх общей геометрии; назначаются при разметке (F-B-01) |
| Места события (нумерованные секторы) | PostgreSQL `seat_inventory` | Одна строка на место, `seat_id` из шаблона; создаётся из зафиксированной версии при создании события |
| Зоны события (стоячие, без нумерации) | PostgreSQL `zone_inventory` | Одна строка на зону: квота и счётчик проданных; продаём количеством (F-C-05) |
| Статусы мест | Redis (4.2.2) + PostgreSQL | Поверх геометрии; в шаблоне их нет |

Структура JSON (упрощённо). Секторы двух типов: `numbered` — с рядами и местами (F-C-04), `standing` — зона без рядов, продаётся количеством (F-C-05):

```json
{
  "venue_id": "vn_01",
  "version": 3,
  "updated_at": "2026-09-01T10:00:00Z",
  "sectors": [
    {
      "id": "A",
      "name": "Партер",
      "type": "numbered",
      "rows": [
        {
          "id": "12",
          "seats": [
            { "id": "A-12-05", "x": 340, "y": 210 }
          ]
        }
      ]
    },
    {
      "id": "F",
      "name": "Фан-зона",
      "type": "standing",
      "x": 120, "y": 640
    }
  ]
}
```

Правила структуры:

- `seat_id` = `{сектор}-{ряд}-{место}` (например `A-12-05`) — единый формат идентификации места во всех хранилищах: `seat_inventory.seat_id`, ключ Redis `seat:{event_id}:{seat_id}`, поле `seat` в API-ответах (5.3) и QR-билете. Только для секторов `numbered`.
- Сектор `standing` — только `id`, имя и координаты для отрисовки: рядов и мест нет. Его `id` становится `zone_id` в `zone_inventory` и полем в HASH Redis `avail:{event_id}`.
- Ценовых категорий и цен в шаблоне **нет** — это слой события: `seat_inventory.category/price` и `zone_inventory.category/price` назначаются при разметке и могут отличаться от события к событию при одной геометрии.
- Координаты `x, y` — только для отрисовки клиентом; сервер их не интерпретирует.
- Валидация при загрузке (Organizer Service): уникальность `seat_id`, связность секторов, лимит на число мест (80 000 — 09-testing).

## 4.3 Топология хранилищ

### 4.3.1 PostgreSQL: один кластер

Работаем на одном кластере. Шардирование не требуется — запасы одного кластера перекрывают целевой масштаб (расчёты ёмкости и нагрузки — 03-sizing 3.2, 3.4); конкурентный захват мест разрулен в Redis до PostgreSQL (ADR-001).

Партиции: orders, tickets, payments, audit_log — месячные, hot-окно 12 месяцев, старше — архив в S3 (Parquet, 3.4).

Когда пересмотреть: устойчивая запись > 1 000 заказов/с (сейчас ~40) или hot-объём > 2 ТБ (сейчас ~117 ГБ, 03-sizing) — порог шардирования. Ключи: `seat_inventory` по `event_id`, `orders`/`tickets`/`payments` по `user_id`.

### 4.3.2 Redis: два кластера — booking и cache

Redis тоже обходимся без шардирования по доменам: делим на два независимых кластера по роли — так делают на практике (изоляция критичного пути от кэша):

| | Redis-booking (критичный путь) | Redis-cache (всё остальное) |
|---|---|---|
| Данные | `seat:*`, `zone_hold:*`, `seats:*`, `avail:*`, `user_hold:*`, `wr:*` | `sess:*`, `jwt_bl:*`, `rl:*`, `cache:*`, `search:*`, `neg:*` |
| Роль | оперативное состояние бронирования: холды, карты и счётчики доступности, очередь | кэш и служебные TTL-ключи: каталог, поиск, сессии, rate-limit |
| Персистентность | не нужна: холды живут 10 мин, карты и счётчики перестраиваются из PostgreSQL (reconciler) | не нужна: rebuild из источников |

Почему два кластера, а не один:

1. **Изоляция нагрузки.** Шторм кэша (cache stampede, eviction-волна на `cache:*`) не должен задушить холды — это денежный путь. В общем кластере пик чтения каталога конкурирует с Lua-скриптами бронирования за CPU и память нод.
2. **Разные политики памяти.** Для холдов eviction недопустим, а кэшу он необходим; в одном инстансе политика одна (4.4.2).
3. **Независимое масштабирование и настройки.** Booking-кластер размеряется под онсейлы (прогрев карт, N-23), cache — под каталог и сессии; лимиты памяти, алерты и деплой у них разные.

Топология кластеров (мастера/реплики, failover) и допустимая потеря данных (RTO/RPO) — [06-reliability](06-reliability.md) (6.1, 6.2). Ёмкость и пик нагрузки — 03-sizing (3.4, 3.7).

## 4.4 Стратегия кэширования

Кэш — трёхслойный: **CDN edge** (общедоступная статика и карточки), **Redis** (горячие API-данные), **негативный кэш** (отсечение ботов от PostgreSQL). Диффы доступности и PDF-билеты не кэшируются.

### 4.4.1 Что кэшируем

| Данные | Слой | Паттерн | TTL / инвалидация |
| --- | --- | --- | --- |
| Каталог, карточка события | CDN + Redis | Cache-aside (Redis) + CDN edge | Redis TTL 5 мин; инвалидация событием `EventUpdated` из Kafka. CDN TTL 60 с + `stale-while-revalidate` |
| Доступность мест (схема зала) | Redis | Redis как источник истины для горячих событий + агрегированный счётчик свободных мест (по секторам) | Полная схема отдаётся из Redis; агрегат `free_count` инвалидируется при каждом hold/sell/release. Холодные события — lazy-прогрев из PostgreSQL |
| Результаты поиска | Redis | Кэш популярных запросов | TTL 60 с (поиск допускает лёгкую неактуальность) |
| Сессии, JWT-blacklist, rate-limit счётчики | Redis | TTL-ключи | TTL = TTL сущности |
| Waiting room (позиция в очереди) | Redis | ZSET по event_id | TTL 30 мин, heartbeat клиента продлевает |
| Изображения, шаблоны схем залов | CDN | Иммутабельные ключи (версия в URL, ADR-004) | Кэш навсегда |

**Что НЕ кэшируем (состав origin-трафика — 03-sizing 3.5):**

| Данные | Почему | Как отдаём |
| --- | --- | --- |
| Диффы доступности (live-статусы мест) | Живые статусы мест — кэшировать нельзя (ADR-004) | Напрямую с origin — главный origin-поток (03-sizing 3.5) |
| PDF-билеты | Персональные файлы покупателя | Presigned URL с S3 напрямую, без edge-кэша |

### 4.4.2 Политики памяти и eviction

Политика вытеснения (`maxmemory-policy`) задаётся на уровне кластера и определяется тем, чем кластер является для системы (4.3.2): booking хранит оперативное состояние бронирования, cache — только перестраиваемые данные.

| Кластер | Политика | Почему |
| --- | --- | --- |
| Redis-booking | `noeviction` | Выкинутый ключ холда = потерянная бронь. При заполнении памяти Redis отклоняет новые записи (`OOM command not allowed`), но не удаляет существующие ключи; срабатывает алерт на evicted > 0 (A-5) |
| Redis-cache | `allkeys-lru` | Вытеснение самых холодных ключей безопасно: `cache:*`, `search:*`, `sess:*` перестраиваются из источников. |

### 4.4.3 Защита от проблем кэша

- Cache stampede (собачья конница) на горячей карточке — `SET NX` + короткий лок на пересчёт, остальные получают stale.
- Penetration (запросы несуществующих id от ботов) — bloom-фильтр на gateway + негативный кэш (TTL 30 с).
- Avalanche — джиттер TTL ±20%.

### 4.4.4 Согласованность Redis и PostgreSQL для мест

Redis — лидер по холдам (быстрый путь), PostgreSQL — лидер по sold. Фоновый reconciler (раз в 5 мин) сверяет hold-места с заказами: холд без заказа старше 10 мин → принудительный release; расхождения sold → алерт (это симптом бага, N-14). Жизненный цикл холда — [ADR-001](../adr/ADR-001-seat-reservation.md).
