# 9. Тестирование

Проверяем систему на четырёх уровнях: выдерживает ли она нагрузку (9.1), переживает ли отказы (9.2), соблюдает ли договорённости между сервисами и требования безопасности (9.3), восстанавливается ли после потери региона (9.3).

## 9.1 Нагрузочное тестирование

### Что и на чём тестируем

| Параметр | Значение |
| --- | --- |
| Инструмент нагрузки | k6 (сценарии) + собственный генератор схем залов |
| Стенд | тестовый, половина мощности прода |
| Платёжный провайдер | в тестовом (sandbox) режиме |
| Данные | синтетический стадион на 80 000 мест + 30 000 реальных событий |

### Профили нагрузки

| # | Тест | Нагрузка | Критерии приёмки |
| --- | --- | --- | --- |
| T1 | Обычный день | 20 чтений/с, 2 попытки брони/с, 0,3 заказа/с — 1 час | Все задержки в рамках N-09…N-12, доля ошибок < 0,1% |
| T2 | **Пик продаж (главный)** | За 5 мин рост с 0 до 40 000 пользователей; 10 000 чтений/с, 4 000 попыток брони/с (~60 успешных), 40 заказов/с; держим 30 мин | Задержка брони p99 ≤ 1,5 с, чтения p99 ≤ 800 мс, доля ошибок < 0,5%, **двойных продаж нет**, серверы добавились за ≤ 10 мин (N-22) |
| T3 | Резкий скачок | Мгновенный рост нагрузки в 10 раз, без разгона | Виртуальная очередь принимает излишек, покупка не деградирует (доля ошибок < 1%), лишние запросы получают 503 с указанием, когда повторить |
| T4 | Длительный прогон | 30% от пика, 8 часов | Нет утечек памяти и соединений, Redis ничего не вытесняет, отставание Kafka не растёт |
| T5 | Одно горячее событие | Вся нагрузка на одно событие (стадион) | CPU основной БД < 70%, ожидание блокировок p99 < 50 мс, брони идут через Redis без просадок |
| T6 | Массовые возвраты | Отмена стадиона: 40 000 возвратов за час | Возвраты идут через очередь с ограничением скорости, покупка других событий не деградирует |
| T7 | Поиск предела | Плавный рост нагрузки до отказа | Известны точка отказа и режим деградации; система восстанавливается сама, без ручного вмешательства |

### Проверяем не только скорость, но и корректность

В тестах T2 и T5 после прогона проверяем SQL-запросами, что:

- каждое место продано не более одного раза;
- сумма оплаченных заказов равна сумме платежей провайдера;
- число выпущенных билетов равно числу оплаченных заказов.

## 9.2 Проверка отказов (Chaos)

Цель — убедиться, что система переживает сбои. Сначала ломаем на тестовом стенде (Chaos Mesh / Litmus), затем проводим контролируемые учения на проде вне часов пик.

| # | Что ломаем | Ожидаемое поведение |
| --- | --- | --- |
| C1 | Основной узел PostgreSQL | Авто-переключение за ≤ 60 с; ни один подтверждённый заказ не потерян; холды в Redis не затронуты |
| C2 | Мастер Redis (холды) | Авто-переключение за ≤ 60 с; статусы мест перестраиваются; холды из окна потери проверяются по PostgreSQL при подтверждении; двойных продаж нет |
| C3 | Основной платёжный провайдер недоступен | Автоотключение за ≤ 30 с, новые платежи идут через резервного провайдера; задержки подтверждений не роняют заказы |
| C4 | Задержка сети 300 мс между сервисом оплаты и Kafka | Механизм надёжной доставки буферизует события; заказы не дублируются; всё восстанавливается само |
| C5 | Потеря целой зоны доступности | k8s переносит сервисы, PostgreSQL/Kafka/Redis переключаются на реплики; покупка восстанавливается за ≤ 15 мин (N-16) |
| C6 | Сервис билетов не работает 30 мин | Растёт отставание (алерт A6); после восстановления догоняет без дублей билетов |
| C7 | Сбой механизма очистки холдов (все холды истекают разом) | Источник истины — TTL в Redis; места становятся доступны; read-модель чинится сверкой за ≤ 5 мин |
| C8 | Расхождение часов на части узлов (+2 мин) | TTL и токены не дают ложных истечений и подтверждений (допуск настроен), срабатывает алерт |

Правила проведения:

- Ограничиваем зону воздействия: сначала один сервис, потом 10% системы, потом целая зона.
- Есть кнопка аварийной остановки эксперимента.
- Эксперимент засчитан, только если SLO не нарушены — либо нарушение задокументировано и устранено до следующего прогона.

## 9.3 Другие виды тестов

| Вид | Что проверяем |
| --- | --- |
| Контрактные | Совместимость API (Pact для REST) и схем событий (проверка в CI). Ломающее изменение контракта останавливает пайплайн |
| Повторные операции | Повтор вебхука ×10, двойной клик при покупке, повтор из Kafka — эффект один |
| Безопасность | Подделка QR (неверная подпись → INVALID), повторный проход по билету, доступ к чужим заказам, обход лимитов, случайные данные в схеме зала |
| Восстановление региона (DR) | Раз в квартал по плану из 6.3: реальное переключение и замер фактического RTO/RPO |
