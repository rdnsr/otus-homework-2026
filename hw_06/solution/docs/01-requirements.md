# 1. Требования

Мы проектируем онлайн-платформу продажи билетов на мероприятия — сервис уровня Qtickets или Yandex Afisha: покупатель находит событие, выбирает места на схеме зала, бронирует и оплачивает их, а на входе контролёр сканирует QR-код билета. Организаторы через ту же платформу публикуют мероприятия и следят за продажами.

Специфика домена — экстремально неравномерная нагрузка. Референс по объемам  взят с открытой статистики билетного оператора Qtickets за 2024 год: 4,24 млн проданных билетов, ~76 тыс. мероприятий. Большую часть времени платформа живёт именно этим хвостом, но старт продаж крупного стамероприятия создаёт всплеск трафика в сотни раз выше среднего. Проектная цель —  **×4** от референса: ~17 млн билетов в год, средний read-поток **20 RPS**, пик на онсейлах **10 000 RPS** (пик-фактор ×500 — онсейл это редкое, но экстремальное событие).

## 1.1 Функциональные требования

Акторы:

- **Покупатель** (F-C-xx)
- **Организатор** (F-B-xx)
- **Контролёр на входе** (F-E-xx)
- **Администратор платформы** (F-A-xx)
- **Внешние системы** (F-S-xx): СКУД площадок — системный актор, вызывает API платформы

## 1.3 Риски и ограничения

| Риск | Вероятность | Чем опасен | Как снижаем |
| --- | --- | --- | --- |
| Всплеск на старте продаж: за пару минут нагрузка вырастает в сотни раз | Высокая | Сайт не выдерживает, люди не могут купить | Виртуальная очередь: пускаем покупателей контролируемыми порциями; кэшируем каталог; автоматически добавляем серверы (N-22) |
| Место продано дважды (оверселл) | Средняя | Скандал, массовые возвраты | Место резервируется атомарно (одновременные попытки не могут занять одно место), повторная проверка в базе, автоматическая сверка, алерт при первом же случае (N-14) |
| Платёжный провайдер недоступен или тормозит | Средняя | Теряем выручку в самый дорогой час | Оплата идёт асинхронно через очередь, есть резервный провайдер, место держится 10 минут — оплата успевает |
| Боты и перекупщики на старте продаж | Высокая | Обычные покупатели не могут купить | Ограничение частоты запросов, капча, лимит билетов на аккаунт и карту, анализ подозрительной активности (N-20) |
| Отмена события: много возвратов сразу | Низкая | Перегрузка возвратов и платёжного провайдера | Очередь возвратов с ограничением скорости, обработка пакетами |
| Подделка QR-кода | Средняя | На вход проходят недействительные билеты | QR подписан секретным ключом, который есть только у нас; приложение проверяет подпись; билет можно использовать один раз |
| Плохой интернет на площадке | Высокая | Очереди на входе | Приложение скачивает список билетов заранее и проверяет офлайн; результаты уходят на сервер, когда связь появится |
| Ограничение: лицензия на платёжную деятельность | — | Нельзя принимать и хранить деньги покупателей | Работаем как посредник: деньги идут через платёжного провайдера, он же выплачивает организаторам |

## 1.4 Backlog (НЕ входит в scope)

| Фича | Почему отложено |
| --- | --- |
| Сезонные абонементы | Другая биллинговая модель |
| Мультивалютность и международные платежи | Комплаенс, налоги |
| Apple/Google Wallet (пуш билетов в кошельки) | Отдельная интеграция с Wallet API и выпуск pass-файлов; на текущем этапе не принципиальна — PDF-билет с QR полностью закрывает контроль доступа. Ticket Service проектируем с расширяемым форматом билета |
| Подарочные сертификаты (электронные кошельки) | Отдельная биллинговая модель: выпуск, погашение, сроки действия |
| Подключение организатором своего приёма платежей | Все деньги идут через платёжного провайдера платформы: только так работают авто-возвраты при отмене (F-A-03), удержание нашей комиссии и единые требования безопасности платежей. Для крупных организаторов. |
| Синхронизация журналов сканов между контролёрами (device-to-device) | Нужна только большим площадкам с многими входами и без интернета: журналы сканов сливаются напрямую между устройствами или через локальный хаб, чтобы один билет не прошёл дважды на разных входах. В базовом scope дубли между устройствами детектируются постфактум на сервере |
| Своя касса/турникеты (железо) | Разработка и эксплуатация собственного железа контроля доступа. СКУД площадок остаётся внешней системой: платформа предоставляет только REST API валидации билетов (F-S-01) — он входит в базовый scope |
| Внешний антифрод/антибот-провайдер (DataDome-аналог) | Отдельная внешняя интеграция усложняет архитектуру; на текущем этапе не принципиальна. |
| Промокоды | Отдельный механизм выпуска/погашения кодов со скидками; на текущем этапе не принципиален |
