# 6. Надёжность

Надёжность держим на двух уровнях и не смешиваем их:

- **HA внутри прод-региона** — переживаем отказ узла или целой зоны доступности (AZ), оставаясь в том же регионе. Восстановление автоматическое, счёт идёт на минуты.
- **DR (Disaster Recovery)** — переживаем потерю всего региона и поднимаемся в отдельном DR-регионе. Дольше (часы), часть шагов ручная.

Оценки — для команды **без круглосуточного NOC**: частые сбои закрывает автоматика, редкие — дежурный по runbook. Где время зависит от человека, это отмечено. Целевые потолки задают N-16 (сбой AZ) и N-17 (потеря региона).

## 6.1 RTO/RPO по сервисам

### 6.1.1 Сбой зоны доступности (AZ), прод-регион

Одна из трёх AZ недоступна, остальные живы. Восстановление автоматическое, дежурный подтверждает результат. Потолок N-16 — бронь и оплата ≤ 15 мин.

| Сервис / данные | RTO | RPO | Как восстанавливаем | Обоснование |
| --- | --- | --- | --- | --- |
| Payment, Order, Booking (payments, orders, seat_inventory) | ≤ 15 мин | **0** | Авто-failover PostgreSQL (30–60 с), перенос подов, проверка инвариантов | Деньги и места: RPO=0 через синхронные реплики (N-15); 15 мин — потолок N-16 |
| User Service | ≤ 15 мин | ≤ 5 мин | Авто-failover PostgreSQL, рестарт подов | Потеря свежей регистрации не критична — пользователь перелогинится |
| Catalog / Search / Availability (read-path) | ≤ 5 мин | 0 (перестраивается) | Поды переносятся, реплики Redis/Elasticsearch | Read-модели перестраиваются из PostgreSQL/Redis |
| Redis-booking (холды, карты мест, очередь) | ≤ 5 мин | до 10 мин | Sentinel-failover (30–60 с), прогрев карт | Потеря холдов = повторный выбор; sold-статусы rebuild из PostgreSQL |
| Redis-cache (сессии, rate-limit, кэш) | ≤ 5 мин | 0 | Sentinel-failover | Кэш перестраивается из источников |
| Kafka | ≤ 5 мин | 0 | Выбор нового лидера партиции | RF=3 и min.insync.replicas=2 — потеря брокера прозрачна |
| Ticket Service | ≤ 15 мин | 0 | Рестарт подов, failover PostgreSQL | Билеты в PostgreSQL + S3, перевыпускаются |
| Notification | ≤ 30 мин | ≤ 15 мин | Рестарт воркеров, replay из Kafka | Уведомления догоняются из Kafka |
| ClickHouse (аналитика) | ≤ 24 ч | ≤ 1 ч | Перезапуск / rebuild | Не влияет на продажи |

Ориентир по времени: авто-failover БД 30–60 с + перенос/рестарт подов 1–5 мин + проверка инвариантов ~5 мин ≈ 10–15 мин на критичный путь.

### 6.1.2 Потеря региона (DR)

Прод-регион целиком недоступен. Поднимаемся в DR-регионе, часть шагов ручная. Потолок N-17 — бронь/оплата ≤ 4 ч, чтение ≤ 6 ч, RPO ≤ 15 мин.

| Сервис / данные | RTO | RPO | Обоснование |
| --- | --- | --- | --- |
| Booking / Order / Payment | ≤ 4 ч | ≤ 15 мин | Promote async-реплики PostgreSQL в DR + развёртывание из IaC; окно закрывает сверка с PSP |
| Ticket Service | ≤ 4 ч | ≤ 15 мин | Поднимается вместе с booking-path; билеты перевыпускаются |
| User Service | ≤ 4 ч | ≤ 15 мин | Разворачивается из IaC |
| Catalog / Search / Availability (read-path) | ≤ 6 ч | ≤ 15 мин | Rebuild Elasticsearch/Redis из PostgreSQL, прогрев кэшей |
| Redis (оба кластера) | ≤ 4 ч | до 15 мин | Поднимаются пустыми, состояние rebuild из PostgreSQL |
| Kafka | ≤ 4 ч | ≤ 15 мин | Брокеры разворачиваются из IaC; сообщения за окно репликации могут отсутствовать |
| Notification | ≤ 4 ч | ≤ 15 мин | Replay из Kafka после восстановления |
| ClickHouse (аналитика) | ≤ 24 ч | ≤ 1 ч | Rebuild из Kafka/S3, не критична |

Важно: эти цифры достижимы только при отлаженном IaC и регулярных учениях. Без них RTO растёт, поэтому учения из 6.3 — обязательное условие, а не пожелание.

## 6.2 Репликация и отказоустойчивость хранилищ

Внутри прод-региона всё разнесено по трём AZ: отказ одного узла или зоны не останавливает продажи, а данные лежат в нескольких копиях.

### 6.2.1 PostgreSQL — источник истины

Как устроены реплики. Есть один **primary** — узел, принимающий запись. Остальные — **реплики (standby)**: полные копии, которые получают журнал изменений (WAL) и повторяют его. Реплика копирует **единственный** primary (а не «свой» отдельный), различается лишь режимом подтверждения:

- **синхронная** — primary ждёт, пока реплика подтвердит запись, и только тогда отвечает «готово» → подтверждённые данные не теряются (RPO = 0);
- **асинхронная** — primary отвечает сразу, реплика догоняет позже → быстрее, но при аварии часть последних записей может потеряться.

Топология:

| Узел | Где | Роль | Зачем |
| --- | --- | --- | --- |
| pg-primary | AZ-1 | запись | Все транзакции |
| pg-standby-1 | AZ-2 | синхронная реплика (кандидат) | Подтверждает коммиты → RPO = 0 |
| pg-standby-2 | AZ-3 | синхронная реплика (кандидат) + чтение | RPO = 0 без блокировки записи при потере AZ-2; разгрузка чтения |
| pg-dr | DR-регион | асинхронная реплика (малый класс) | Основа восстановления региона |

Одновременно работает **1 primary + 3 реплики** (2 в прод-регионе + 1 в DR).

Настройки:

- `synchronous_commit = remote_apply` — коммит подтверждается после того, как реплика применила WAL (+2–5 мс к commit latency, вписываемся в N-11).
- `synchronous_standby_names = 'ANY 1 (pg-standby-1, pg-standby-2)'` — достаточно подтверждения **любой одной** из двух реплик. Это ключевой момент: падение одной AZ не блокирует запись, и RPO = 0 сохраняется. Будь синхронная реплика одна, её отказ остановил бы платежи до ручного вмешательства — поэтому кандидатов два.
- Чтение (отчёты, аналитика) идёт с реплик, чтобы не нагружать primary.

Управление и failover:

- **Кто управляет:** Patroni на каждом узле + DCS-кворум (etcd/Consul) из 3 узлов, по одному в каждой AZ. Patroni держит «замок лидера» в DCS и при отказе primary автоматически назначает нового. Кворум нужен, чтобы два узла не объявили себя лидерами одновременно (split-brain) — для денег это недопустимо.
- **Если self-hosted не нужен:** managed PostgreSQL провайдера даёт то же (primary + standby + авто-failover) без эксплуатации DCS своими силами; для малого штата это предпочтительнее.
- Failover: 30–60 с.

Бэкапы и PITR:

- WAL-архив непрерывно (PITR на 30 дней) + полный снапшот ежедневно; хранение 35 дней; шифрование; копия в DR-регион (async, алерт при lag > 5 мин).
- Раз в квартал — проверка восстановления из бэкапа: наличие архива само по себе ничего не гарантирует.

### 6.2.2 Redis — холды и кэш

Два независимых кластера по роли (04.3.2), в каждом **1 master + 2 реплики** (3 узла, по одному в каждой AZ). Реплики — полные копии мастера; при отказе мастера одну из них повышают до мастера.

| Кластер | Состав | Политика | Данные | Восстановление |
| --- | --- | --- | --- | --- |
| redis-booking | 1 master + 2 replicas, 3 AZ | `noeviction` | холды, карты мест, счётчики, waiting room | Sentinel-failover 30–60 с; холды теряются → пользователь выбирает заново |
| redis-cache | 1 master + 2 replicas, 3 AZ | `allkeys-lru` | сессии, rate-limit, кэш каталога/поиска | Sentinel-failover; перестраивается из источников |

Про «много мастеров и для какого мастера реплика»:

- В **Redis Cluster** данные делят по слотам между несколькими мастерами (шардами), и каждая реплика копирует **свой** мастер. Отсюда «3 мастера + 3 реплики» = 3 пары «мастер–реплика»; мастер нужен для горизонтального шардирования.
- Нам шардирование не нужно: объём данных ~1,5–2 ГБ, пиковая нагрузка ~12–24 тыс. операций/с, а один узел Redis держит 50–100 тыс. операций/с. Поэтому вместо Cluster берём простую репликацию с Sentinel: один мастер и две его реплики в разных AZ — дешевле и проще, а отказоустойчивость та же (мастер в одной AZ, реплики в двух других).
- Персистентность не нужна: холды живут 10 мин (TTL), карты и счётчики перестраиваются из PostgreSQL (reconciler), кэш — из источников.

### 6.2.3 Kafka — шина событий

Простым языком: Kafka хранит поток событий (заказ создан, оплата подтверждена и т.п.) и раздаёт их сервисам. Данные топика делят на **партиции**, а каждая партиция лежит на нескольких **брокерах** (серверах) — это и есть копии.

| Параметр | Что значит простыми словами |
| --- | --- |
| **RF = 3** (replication.factor) | Каждая партиция хранится в **трёх копиях** на трёх брокерах в трёх AZ. Теряем один брокер или целую AZ — данные целы |
| **min.insync.replicas = 2** | Запись принимается, только если её подтвердили **минимум 2 копии из 3**. Если жива лишь одна — брокер отклоняет запись (лучше остановиться, чем потерять сообщение). Для платёжных топиков это осознанный выбор |
| **acks = all** | Отправитель считает сообщение отправленным, только когда его подтвердили **все синхронные копии**. В паре с предыдущим пунктом: сообщение не потеряется при отказе одного брокера |

Итог: потеря брокера или AZ для продаж прозрачна; потеря двух брокеров останавливает запись в платёжные топики (данные важнее доступности). Отставание потребителей контролируем метрикой `kafka_consumer_lag` (алерт A6).

### 6.2.4 Elasticsearch — поиск (некритичен)

Данные — поисковый индекс (read-model), который полностью перестраивается из PostgreSQL/Kafka. Недоступность поиска не останавливает продажи, поэтому здесь всё проще:

- **Реплики:** на каждый primary-шард — **1 replica shard** (копия шарда на другом узле). Если узел упадёт, реплика станет основной. Нужно минимум 2 data-узла в разных AZ.
- **Бэкап:** снапшот в S3 **раз в сутки** (было ежечасно — для некритичных данных избыточно).
- **Основной путь восстановления** — не снапшот, а rebuild из PostgreSQL/Kafka за ~1–2 ч; снапшот лишь страховка.

### 6.2.5 S3 — объектное хранилище

S3 у нас — **критичная зависимость для восстановления**, хотя и не для онлайн-продаж. Здесь лежат:

- пользовательские файлы: изображения событий, шаблоны схем залов, PDF-билеты, манифесты СКУД;
- холодный архив ClickHouse (Parquet);
- **бэкапы БД: непрерывный WAL-архив и ежедневные снапшоты** → без S3 нет PITR.

Что означают термины:

- **versioning** — хранятся все версии объекта. Перезапись или удаление не уничтожает предыдущую версию: защита от случайного удаления и от «шифровальщиков»; можно вернуть прежнюю версию.
- **cross-region replication (CRR)** — объекты автоматически и асинхронно копируются в бакет в DR-регионе. Это и есть «реплика S3», но **для DR**, а не для ускорения внутри региона.

Что будет, если S3 недоступен:

- **Внутри региона** отдельная реплика не нужна: S3 у провайдера изначально хранит данные в нескольких AZ (durability 99,999999999%). Потеря одной AZ данные не теряет.
- **Потеря региона** → переключаемся на бакет в DR, куда всё скопировано через CRR.
- **Влияние на продажи:** изображения и шаблоны отдаются через CDN (кэш), продажи идут; PDF-билеты при недоступности S3 не скачать (деградация, повтор позже); PITR недоступен, пока S3 лежит, но сама БД работает.
- CRR асинхронна → у копии в DR есть лаг; его измеряем и алертим (часть DR-RPO).
- Для защиты бэкапов от удаления — `object lock` (WORM) на бакет с WAL и снапшотами.

## 6.3 План DR (потеря региона)

Архитектура: **прод-регион + pilot light в DR**. Постоянно в DR работает только async-реплика PostgreSQL (малый класс); остальные сервисы разворачиваются из IaC по требованию (Terraform + Helm, всё в Git). Так дешевле и проще для малого штата, чем держать warm standby, а RTO остаётся в лимите N-17. Мультимастер осознанно не строим (бюджет/сложность, риск split-brain для мест).

| Шаг | Действие | Время |
| --- | --- | --- |
| 1. Детект | Health-checks региона + ручное подтверждение (защита от ложного failover) | 15–30 мин (ночью дольше) |
| 2. Данные | Promote async-реплики PostgreSQL в DR (потеря ≤ 15 мин данных — RPO; платежи сверяются с PSP по API перед открытием продаж) | 30–60 мин |
| 3. Сервисы | Развернуть booking-path (Booking, Order, Payment, Ticket) + Kafka из IaC | 60–90 мин |
| 4. Трафик | Переключение DNS (TTL 60 с) на DR-ingress | 15–30 мин |
| 5. Read-path | Прогрев кэшей, rebuild Elasticsearch/Redis из PostgreSQL | параллельно, +2–4 ч |
| **Итого** | **Booking-path доступен за ≤ 4 ч (N-17), read-path полноценно за ≤ 6 ч** | |

**Сверка с PSP после DR:** перед открытием продаж — reconciliation-джоба: все заказы `PENDING_PAYMENT` старше 10 мин отменяются, оплаченные по данным PSP, но не подтверждённые у нас — подтверждаются вручную из выгрузки PSP. Это закрывает окно RPO 15 мин без оверселла.

**Учения:** DR-учения (game day) раз в квартал: реальное переключение read-path на DR в тестовом окне, замер фактического RTO/RPO; цель — уложиться в 2 ч вместо 4. Без учений pilot light опасен: IaC «протухает», и деплой в DR может не сработать в нужный момент. Учения — обязательное условие, а не пожелание.

## 6.4 Деградация в штатной работе

- Недоступность Notification/Search/Analytics не влияет на продажи.
- Деградация Availability → схема зала из CDN-кэша шаблона с дисклеймером.
- Деградация PSP → фейловер на резервный PSP (ADR-003).
- Недоступность S3 → продажи идут, PDF-билеты не скачать (повтор позже), PITR временно недоступен.
