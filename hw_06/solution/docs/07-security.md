# 7. Безопасность

## 7.1 Аутентификация (Keycloak)

| Субъект | Механизм |
| --- | --- |
| Покупатели | OIDC/OAuth2: email+пароль (Argon2id), соцсети (Google/Apple/VK ID). Access token — JWT (RS256, 15 мин), refresh token — rotating, httpOnly cookie, revoke-лист в Redis |
| MFA | TOTP/SMS-OTP: смена email/телефона, возврат, вход с нового устройства |
| Организаторы | Отдельный realm, обязательная MFA, верификация юрлица админом до публикации событий |
| Администраторы | Отдельный realm, аппаратная MFA, доступ только из VPN/office IP |
| Сервис ↔ сервис | mTLS (service mesh, SPIFFE-ID); внутренние API закрыты снаружи (NetworkPolicy) |
| СКУД площадок | API keys per venue, scope `tickets:validate`, ротация 90 дней |

## 7.2 Авторизация

- **RBAC** в IdP: роли `buyer`, `organizer`, `support`, `admin`, `scanner`.
- **ABAC:** организатор видит только свои события (`organizer_id`), проверка в сервисе, не только на gateway.
- **Object-level:** заказ/билет доступен только владельцу (`user_id`).
- **Наименьшие привилегии:** Payment не имеет доступа к таблицам пользователей; Ticket — только к tickets.

## 7.3 Шифрование и секреты

| Слой | Мера |
| --- | --- |
| In transit | TLS 1.3 (HSTS) снаружи, mTLS внутри mesh; webhook PSP — HMAC-подпись + IP allowlist |
| Персданные (152-ФЗ) | email/phone — envelope encryption, ключ в KMS; хранение в РФ-регионе; удаление — crypto-shredding |
| Пароли | Argon2id, per-user соль, pepper в KMS |
| Секреты приложений | Vault: динамические креды БД (TTL 24 ч), ротация ключей PSP/шлюзов; инъекция через sidecar, ничего в git/env |
| QR-подписи билетов | Ed25519: приватный ключ на сервере (Vault), публичный — на устройствах контролёров; проверка офлайн. Утечка ключа — ротация + перевыпуск манифестов (runbook) |

## 7.4 PCI DSS

- CDE-зона отсутствует: карточные данные не проходят через нашу инфраструктуру
- Токенизация на стороне PSP, у нас только токены и последние 4 цифры
- Сертификация — SAQ A
- Резервный PSP — по той же схеме

## 7.5 Антибот и антифрод (N-20)

1. **Edge:** CDN/WAF, rate limiting по IP/сессии/аккаунту (Redis sliding window), блокировка датацентровых ASN на booking-path.
2. **Waiting room:** на onsale — очередь с рандомизацией позиции после старта, один слот = одна сессия.
3. **Бизнес-лимиты:** ≤ 6 билетов на заказ, лимит на аккаунт/карту/телефон на событие.
4. **Пост-фрод:** velocity-правила (карта × аккаунты × IP), авто-отмена подозрительных заказов до выпуска билетов, возврат мест в продажу.
