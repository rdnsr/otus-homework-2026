# ADR-003: Асинхронная оплата через Saga + Transactional Outbox

**Статус:** Принято · **Дата:** 2026-09-03 · **Контекст:** Booking, Payment, Ticket, Order сервисы

## Контекст

Оплата — внешняя зависимость с переменной latency (300 мс — 60 с с 3DS, N-12) и периодическими деградациями. Синхронная цепочка «заказ → оплата → билет» в одной распределённой транзакции невозможна (2PC через PSP не существует), а синхронное ожидание PSP в запросе пользователя делает нашу доступность заложником доступности PSP. Требования: ноль потерянных платежей (N-15), идемпотентность ретраев и webhook'ов.

Рассмотренные варианты:

1. Синхронная оркестрация в запросе пользователя.
2. **Saga (оркестрация) + Transactional Outbox + Kafka** (выбран).
3. Хореография без оркестратора.

## Решение

1. Клиент получает `202 Accepted` сразу после инициации платежа (контракт 05.3-3); финальный статус — асинхронно (поллинг `GET /api/v1/orders/{id}` или push).
2. **Saga-оркестратор** в Payment Service ведёт состояние заказа: `PENDING_PAYMENT → PROCESSING → PAID | PAYMENT_FAILED`, шаги-компенсации: неуспех/таймаут → release холда, уведомление; успех после истёкшего холда → авто-возврат.
3. **Transactional Outbox:** каждое изменение состояния и событие пишутся в одной локальной транзакции PostgreSQL; отдельный релей публикует в Kafka → «событие не потеряно» даже при падении сервиса между БД и брокером. Вебхуки PSP дедуплицируются по `idempotency_key` (UNIQUE).
4. Фейловер на резервный PSP по error-rate > 20% (06.4) — заказы в PROCESSING переживают переключение, т.к. состояние в БД, а не в памяти.

## Последствия

**Плюсы:**

- Доступность платформы (N-13) не зависит от доступности PSP: деградация провайдера — не остановка продаж, а очередь PROCESSING.
- Инварианты «платёж ровно один», «заказ не потерян» гарантированы БД и идемпотентностью, а не осторожностью кода.
- Нагрузка всплесков сглаживается Kafka — PSP не получает от нас DDoS в onsale.

**Минусы и как живём:**

- Пользователь не знает результат мгновенно → UX: таймер, пуш «билет готов», честный статус; целевое N-12 (p99 подтверждения ≤ 60 с).
- Сложность компенсаций: каждая ветка (таймаут, частичный успех, дабл-вебхук) покрыта тестами и хаос-экспериментом C4.
- Outbox-релей — ещё один компонент в эксплуатации; его лаг в алертах (A6).

**Альтернатива 1 отвергнута:** таймаут PSP в 60 с при пике 300 заказов/с держит пулы соединений и множит p99; деградация PSP = падение продаж — прямой удар по выручке в самый дорогой час.
**Альтернатива 3 отвергнута:** при 5+ участниках саги хореография размазывает логику компенсаций по сервисам; оркестратор даёт явный state machine, который можно логировать, дебажить и тестировать.
