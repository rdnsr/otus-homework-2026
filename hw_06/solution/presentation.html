Введение

Домен и проблема

Онлайн-платформа продажи билетов уровня Qtickets или Яндекс Афиши: покупатель находит событие, выбирает места на схеме зала, бронирует и оплачивает их, а на входе контролёр сканирует QR-код.

Акторы

  • Покупатель — каталог, выбор мест, покупка, билет
  • Организатор — публикация событий, схемы залов, отчёты
  • Контролёр и СКУД площадки — проверка билетов на входе
  • Администратор — модерация, библиотека шаблонов

Главная особенность — неравномерная нагрузка

Обычный день платформа живёт на «хвосте» событий, но старт продаж популярного концерта даёт всплеск в сотни раз выше среднего.

Производительность (p99)

  • Проверка QR на входе — 500 мс (онлайн), 200 мс офлайн
  • Каталог / карточка события — 500 мс
  • Схема зала / доступность мест — 800 мс
  • Создание брони (hold) — 1,5 с
  • Подтверждение оплаты — ≤ 60 с (асинхронно)

Надёжность и безопасность

  • Доступность платформы — 99,95%
  • Двойная продажа места — 0 случаев
  • RPO платежей — 0; RTO (сбой AZ) — ≤ 15 мин
  • DR: RTO ≤ 4 ч, RPO ≤ 15 мин
  • PCI DSS (SAQ A), 152-ФЗ, антибот: боты ≤ 1% билетов

Ключевые решения

Шесть решений, которые определяют систему

1

Микросервисы + Kafka. Read-path (каталог, поиск, схема зала) масштабируется независимо от write-path (бронь, оплата).

2

Резерв мест в Redis (атомарный Lua, TTL 10 мин) + финальное подтверждение в PostgreSQL — ноль оверселла без блокировок БД.

3

PostgreSQL, один кластер. Шардирование не требуется; синхронная репликация для платежей (RPO = 0).

4

Асинхронная оплата: Saga + Transactional Outbox. Переживаем деградацию PSP без потери заказов, есть резервный провайдер.

5

Виртуальная очередь (waiting room) на старте продаж защищает booking path, впуская контролируемыми порциями.

6

Схема зала — библиотека версионированных шаблонов, цены размечаются на уровне события.

Архитектура

Почему микросервисы + event-driven

Асимметрия нагрузки

Чтение — ~99% трафика (до 10 000 RPS в пике), запись — ~40 RPS. Реплики Availability/Catalog докручиваются под наплыв, не трогая Payment.

Разные требования к консистентности

Заказам и платежам нужен строгий ACID; каталогу, поиску, уведомлениям достаточно итоговой согласованности. Каждый сервис коммитит локальную транзакцию и публикует событие.

Изоляция сбоев

Недоступность поиска, уведомлений или аналитики не останавливает продажи. Kafka развязывает сервисы во времени и буферизует всплески.

Независимые релизы

Сервисы разворачиваются и развиваются по отдельности; контракт взаимодействия — версия события и API (Schema Registry).

Отвергнутые альтернативы: модульный монолит (пик ×500 масштабирует всё приложение целиком), serverless (холодные старты, состояние холдов), чистая синхронная SOA (каскадные отказы, зависимость от PSP).

Ключевое решение · ADR-001

Резервирование мест: Redis hold + PostgreSQL

Контекст

Инвариант — ноль оверселлов. Пик до 4 000 попыток брони в секунду, успешных ~60. Место резервируется на 10 минут и автоматически возвращается в продажу.

Отвергнутые варианты

  • Пессимистичные блокировки в PostgreSQL — очередь блокировок, p99 вне SLO
  • Только Redis — потеря холдов при failover даёт двойную продажу

Уровень 1 — Redis (скорость)

Один атомарный Lua-скрипт: SET seat:{event}:{seat} {hold_id} NX PX 600000. «Все места или ни одного». TTL = дедлайн оплаты, места освобождаются сами.

Уровень 2 — PostgreSQL (истина)

Перевод в SOLD только если место HELD и версия совпала (optimistic locking). Не совпало — авто-возврат денег, место не продаётся. Reconciler сверяет состояние раз в 5 мин.

Ключевое решение · ADR-003

Асинхронная оплата: Saga + Transactional Outbox

Контекст

Платёжный провайдер — внешняя зависимость с latency 300 мс — 60 с (3DS) и периодическими деградациями. Синхронное ожидание PSP сделало бы нашу доступность заложником его доступности.

Решение

  • Клиент получает 202 Accepted сразу; финальный статус — поллингом или пушем
  • Saga-оркестратор в Payment Service ведёт state machine заказа
  • Transactional Outbox: смена статуса и событие пишутся одной транзакцией
  • Идемпотентность webhook по idempotency_key
  • Фейловер на резервный PSP по error-rate > 20%

Компенсации: таймаут или неуспех — release холда; успех после истечения холда — авто-возврат. Доступность платформы (99,95%) не зависит от доступности PSP.

Ключевое решение · ADR-004

Схема зала: библиотека шаблонов + цены события

Геометрия отделена от статусов и цен

Шаблон — только секторы, ряды, места и координаты. Статусы живут в Redis и seat_inventory, цены — в seat_inventory.category/price. Клиент накладывает статусы поверх геометрии по SSE.

Иммутабельность → CDN

Версия в ключе S3 (venues/{venue_id}/seatmap/v{n}.json) — ответ кэшируется в CDN фактически навсегда, Origin почти не видит самого горячего read.

Библиотека версионированных шаблонов

  • Один шаблон на площадку — им пользуются все организаторы
  • Правка создаёт новую версию; старые не удаляются
  • Публикация — только после апрува администратора (DRAFT → APPROVED)
  • Событие фиксирует версию при создании; правка площадки не ломает идущие события

Цены — разметка на уровне события

Одна цена на место, назначается при разметке; доступна до старта продаж, после — только на непроданные места.

Хранение данных

Несколько хранилищ и кэширование

ДоменХранилище
Заказы, платежи, билеты, местаPostgreSQL
Холды, карты мест, очередь, кэшRedis
Поиск и подсказкиElasticsearch
Аналитика продажClickHouse
Статика, PDF, бэкапыS3

PostgreSQL — источник истины (ACID). Шардирование не требуется: запаса одного кластера хватает, ключи event_id / user_id зарезервированы на будущее.

Два кластера Redis

  • booking (noeviction) — холды, карты мест, очередь: вытеснение недопустимо
  • cache (allkeys-lru) — сессии, rate-limit, кэш каталога: перестраивается из источников

Трёхслойный кэш

CDN edge (статика, карточки) + Redis (горячие API-данные) + негативный кэш (отсечение ботов). Диффы доступности и PDF-билеты не кэшируются.

Взаимодействие

Протоколы и ключевые API-контракты

Правило

Все операции с деньгами и местами после подтверждения — асинхронные через события; все пользовательские чтения — синхронные.

  • Клиент ↔ Gateway — HTTPS/REST + JSON
  • Доступность мест — SSE-поток диффов
  • Очередь — polling раз в 20 с
  • Домен — Kafka + Avro + Schema Registry
  • Payment ↔ PSP — REST + подписанные webhooks

Ключевые контракты

  • POST /holds — атомарный холд мест, 409 при занятости
  • POST /orders — заказ в статусе PENDING_PAYMENT
  • POST /payments — 202 Accepted + ссылка на PSP
  • POST /internal/webhooks/psp/{provider} — подтверждение оплаты
  • GET /events/{id}/availability + SSE — доступность мест
  • POST /tickets/validate — валидация QR для СКУД

Идемпотентность всех мутаций — через Idempotency-Key; события — at-least-once, консьюмеры идемпотентны.

Надёжность · Безопасность · Observability

Как держим SLA и контролируем систему

Надёжность

  • HA в 3 AZ: авто-failover PostgreSQL 30–60 с, Redis Sentinel, Kafka RF = 3
  • RTO ≤ 15 мин (сбой AZ), RPO = 0 для платежей
  • DR: pilot light, RTO ≤ 4 ч, RPO ≤ 15 мин, учения ежеквартально
  • Деградация PSP → резервный провайдер

Безопасность

  • Keycloak: OIDC/OAuth2, MFA, отдельные realm для организаторов и админов
  • RBAC + ABAC, object-level доступ к заказам
  • TLS 1.3 снаружи, mTLS внутри, Vault для секретов
  • QR Ed25519 — приватный ключ только на сервере
  • PCI DSS SAQ A: карта не проходит через нас

Observability и тесты

  • Бизнес-метрики: oversell_detected_total = 0 всегда
  • RED (latency, error rate) и USE (репликация, Kafka lag, Redis)
  • 7 алертов, P1 будит дежурного
  • Сквозной трейсинг booking-path 100%
  • Нагрузка k6 (T1–T7) и Chaos (C1–C8)
